# 双语首发与贡献维护

玩家入口为双语README、FAQ及贡献指南。内部运行步骤集中在本文件和PUBLISHING，避免把生产数据库、检查点编号和账号流程塞进工坊功能介绍。

2026-10-31用户确定：普通反馈统一引导到工坊页面留言区，中英文都欢迎，不要求先去GitHub或分讨论主题。公开文案承诺积极维护、认真查看反馈、持续修正问题并跟进游戏更新；不承诺固定回复期限。GitHub模板保留供源码协作使用，不自动发布消息。已移除不用的分类讨论模板及本地HTML预览工具；文案和素材直接维护在workshop目录。

## 接受一次正文贡献

1. 玩家可用任何一种首发语言报告，内部ID不是门槛。若提供地名、地区和截图，用 tools/find_location.py 查找候选；同名地点需在研究库核对身份。
2. 确认地理范围、年代和来源是否真正支持主张。可靠的非维基资料可以作为反馈依据；当前导出来源schema仍使用固定维基修订，不让贡献者为适配格式伪造修订号。
3. 正文PR作为提案审阅，不能直接把发布副本当新的主库。先按原研究工程的AGENTS和锁/导入规则回写主库，保留已有来源、事实和审核证据。
4. 核对英中事实对应。单语言提案可以接受为待配对修改，但不能发布其中一种已经变化、另一种还说旧事实的条目。翻译要自然，不逐词硬译，不自行增加史实。
5. 从同一确认过的研究检查点重新导出整份数据，核对ID、官方保护、正文差异及来源，再更新发布工程。不能为小修擅自升级review_status。
6. 运行相关检查，写双语变更说明，注明贡献者愿意公开的名称。版本和构建目录使用新的值，保留已验收包。

## 首发的发布顺序

一个工坊条目、同一运行包，英文与简体中文同时提供。首发语言不是自动翻译占位，也不分成两个互相覆盖的工坊项目。

先完成本地材料、构建与真实游戏验收；GitHub按所有者选择的账号、仓库和可见性上传。私有GitHub链接不可当作所有玩家都能访问的支持入口，普通反馈直接使用Steam工坊页面留言区。

工坊首次私有上传后保留实际条目ID，核对游戏下载内容再公开。Steam页面可分别设置english与schinese时使用分语言文案；若UI只给一个字段，使用合并双语版。界面不支持的功能不靠猜测或未记录的API参数解决。

## 工坊页面收尾

上传本地准备的封面和真实游戏截图；不要把生成封面当效果证明。确认工坊页面的留言功能正常，页面说明直接引导玩家留言，不以建立三个讨论主题作为首发要求。公告与双语变更说明只在实际发布后发送；目前仅是本地文案，不代表已经发布。

记录版本、游戏build、条目ID、可见性、源码commit、文件/ZIP哈希、两语验收及实际订阅结果。接受条款、邮箱确认和平台审核由真实账号完成，不记录凭据。更新和回滚见UPDATE_AND_ROLLBACK.md。

## 发布证据的机器检查

复制 release-evidence.example.json 到dist下的专用证据目录，填写实际包SHA、版本、游戏build和工坊ID；每个通过项目引用该证据目录内的记录或截图文件及其SHA-256。不创建虚构记录，不把示例中的pending批量改成passed。

预检可传入 --evidence 指向该JSON，并加 --require-publish-ready。工具检查包对应、证据文件及哈希和项目是否齐全；缺项保持未就绪，引用其他包、文件被改动或越出证据目录则失败。它不能独立判断截图真实性和资料正确性，也不授权发布；最终由所有者审阅真实记录。没有提供证据时不会自动判定人工项目通过。
